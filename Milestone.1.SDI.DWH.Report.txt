1. EXECUTIVE SUMMARY & PROJECT CHARTER
================================================================================
Milestone 1 establishes the foundational data engineering platform for a global
pharmaceutical cold-chain supply network. Pharmaceutical cold chains require
uncompromising data fidelity: biological therapeutics, vaccines, and insulin
spoil irreparably if storage conditions deviate from strict 2°C–8°C bounds or if
expiration windows lapse before fulfillment.

The primary objective of Milestone 1 is the delivery of the Sales & Demand
Intelligence (SDI) Data Mart, alongside a production-grade automated pipeline.
The data architecture ingests seven disparate enterprise data sources (comprising
over 933,000 baseline records), validates and stages raw transactions, executes
dimensional transformations into an in-process columnar OLAP warehouse (DuckDB),
and projects operational telemetry and business intelligence through five
interactive Grafana dashboards.


Key Architectural Milestones Achieved:
1. Orchestration: 4 Airflow DAGs automating generation, ingestion, transform,
   and analytical querying with zero manual intervention required.
2. Ingestion Engine: High-throughput batch COPY protocol capable of parsing
   over 50,000 rows/second with automated anomaly and schema rejection.
3. Storage Layer: Dual-tier storage leveraging PostgreSQL 15 for atomic OLTP
   staging and DuckDB 1.1 for vectorized, in-process columnar analytical marts.
4. Business Intelligence: 7 Grafana dashboards — 4 Data Engineering
   operational dashboards (Batch Ingestion, Streaming Telemetry, Storage
   Health, Query Performance) plus 3 Decision-Focused BI Cockpits (Channel
   Margin, Hospital Forecast, Fast/Slow Movers).
5. Oversampling Engine: A deterministic synthetic data engine producing
   two distinct refresh cycles (~46,635 rows per cycle, ~10% data expansion)
   specifically designed to trigger and validate SCD Type 2 dimension updates.

design pattern orchestrated via Apache Airflow 2.10.5. The pipeline separates
landing file discovery, relational staging, columnar analytical dimensionalization,

2.2 Detailed DAG Inventory & Execution Flow
-------------------------------------------

• DAG 01: `dag_01_generate` (Data Generation & Oversampling)
  - Frequency: On-Demand / Parameterized Execution.
  - Parameter: `cycle` (Integer: 1 = Jul-Sep 2025; 2 = Oct-Dec 2025).
  - Purpose: Generates synthetic transactions across all 7 source files with
    strictly enforced foreign-key integrity, cold chain anomalies, and price
    modifications, dropping timestamped CSVs into `data/landing/`.
  - Task Dependency: `generate_data` >> `log_stats`

• DAG 02: `dag_02_ingestion` (Automated File-Watcher & Staging Ingestion)
  - Frequency: Continuous cron schedule (`*/5 * * * *`).
  - Purpose: Scans `data/landing/` for unprocessed CSV files. Validates headers,
    sanitizes data types, executes high-speed PostgreSQL bulk COPY into `stg.*`,
    records batch metrics into `ops.batch_ingestion_log`, logs rejected records
    into `ops.rejected_records_log`, and moves processed files to `data/archive/`.
  - Task Dependency:
    `watch_landing` >> `ingest_master` >> `ingest_manufacturing` >>
    `ingest_delivery` >> `ingest_warehouse` >> `ingest_sales` >>
    `ingest_demand` >> `ingest_iot` >> `archive_files`

• DAG 03: `dag_03_transform` (Dimensional Modeling & BI Synchronization)
  - Frequency: Scheduled after staging ingestion / Manual trigger.
  - Purpose: Executes full dimensional transformation. Connects to PostgreSQL
    staging, builds the DuckDB star schema (9 dimensions, 2 facts), manages
    SCD Type 2 record versioning on `dim_medicine`, executes data quality
    validation rules, and executes the `sync_bi_views` task which pre-computes
    11 executive summary tables into Postgres `bi.*` for Grafana rendering.
  - Task Dependency:
    `create_ddl` >> `build_dim_date` >> `build_dimensions` >>
    `build_fact_sales` >> `build_fact_demand` >> `validate_warehouse` >>
    `sync_bi_views`

• DAG 04: `dag_04_query` (Analytical Benchmark & Constellation Validation)
  - Frequency: Daily / Post-transformation verification.
  - Purpose: Executes 8 targeted OLAP analytical queries and 3 Fact
    Constellation cross-mart queries against DuckDB. Measures query execution
    latency, records performance benchmarks into `ops.query_execution_log`, and
    validates business KPIs (OTIF rates, cold chain breach exposure, profit margins).
  - Task Dependency: `run_olap_queries` >> `run_constellation_queries` >> `log_benchmarks`

2.3 Ingestion Mechanics, File-Watcher & Automated Triggering
-----------------------------------------------------------
The file ingestion mechanism in `dag_02_ingestion` avoids static polling loops
by implementing an idempotent directory-scanning sensor task (`watch_landing`).
At every 5-minute interval:
1. Directory Scan: Python's `pathlib.Path.glob("*.csv")` inspects `data/landing/`.
2. Header & Schema Check: Each file is inspected against expected column counts
   and naming signatures defined in `src/ingestion/loader.py`.
3. High-Speed Bulk Loading: Data is streamed into PostgreSQL using `COPY FROM STDIN`
   via `psycopg2.extras.execute_values` and dedicated CSV buffers, achieving over
   50,000 records/sec throughput without hitting transactional row-lock overhead.
4. Quarantine Mechanism: Corrupted rows or files failing foreign-key sanity
   checks are automatically isolated into `data/rejected/` with comprehensive
   rejection logs committed to `ops.rejected_records_log`.
5. Atomic Archival: Upon successful staging commit, files are moved atomically
   to `data/archive/<timestamp>_<filename>` to ensure zero double-ingestion.

2.4 Data Lineage, Idempotency & Fault Isolation
-----------------------------------------------
Every record flowing through the pipeline is enriched with metadata attributes:
- `SourceFile`: Exact landing file name.
- `IngestionBatchID`: UUID linking the row to `ops.batch_ingestion_log`.
- `StagedTimestampUTC`: Timestamp of physical staging.
- `WarehouseLoadTimestamp`: Injected into DuckDB dimension and fact tables.
Idempotency is maintained through staging table truncation prior to batch ingest
or UPSERT semantics based on business keys (`SalesTransactionID`, `SnapshotID`),
guaranteeing that pipeline restarts or retries never result in duplicate metrics.

3. SECTION B: IMPLEMENTATION CHALLENGES & ENGINEERING SOLUTIONS
================================================================================

3.1 Challenge 1: SQLAlchemy 2.0 vs. Airflow 2.10 ORM Compatibility Clash
------------------------------------------------------------------------
• Symptom / Problem:
  During container initialization and DAG parsing, the Airflow scheduler and
  webserver crashed with fatal errors:
  `MappedAnnotationError: Type annotation for "TaskInstance.dag_model" can't be correctly interpreted`.
• Root Cause:
  The project's `requirements.txt` initially specified `sqlalchemy>=2.0`.
  Apache Airflow 2.10.x relies internally on SQLAlchemy 1.4.x ORM declarative
  type-mapping paradigms. Installing SQLAlchemy 2.0 introduced breaking changes
  in mapped column annotations that crashed the internal metadata store.
• Engineering Solution:
  Pinned the dependency in `requirements.txt` to `sqlalchemy>=1.4.36,<2.0`.
  Rebuilt the custom Airflow Docker image using `docker-compose build --no-cache`,
  restoring metadata DB stability and enabling rapid task scheduling.

3.2 Challenge 2: The DuckDB-Grafana Bridge: Architecting the BI Sync Layer
--------------------------------------------------------------------------
• Symptom / Problem:
  The project chose DuckDB as its high-performance columnar analytical warehouse.
  However, Grafana has no native, officially supported DuckDB database driver.
  Attempting to run an unauthenticated SQLite/ODBC plugin inside Docker caused
  file lock contention (`duckdb.IOException: Could not set lock on file`)
  whenever Airflow wrote to the warehouse while Grafana attempted to read.
• Root Cause:
  DuckDB is an in-process, single-writer columnar engine. External visualization
  tools cannot safely open concurrent read/write connections to an active DuckDB file.
• Engineering Solution:
  Architected a dedicated, automated BI Sync Layer (`src/transform/bi_sync.py`).
  In Step 9 of `dag_03_transform`, after DuckDB validates the star schema,
  DuckDB executes high-speed analytical aggregations (window functions, cross-fact
  joins, moving averages) and streams the aggregated results into a dedicated
  `bi.*` schema in PostgreSQL via `psycopg2`.
  This delivers the best of both worlds:
  1. Heavy dimensional aggregations execute in milliseconds inside DuckDB's vectorized engine.
  2. Grafana connects seamlessly to PostgreSQL `bi.*` using the native, highly optimized Postgres datasource.

3.3 Challenge 3: Path Resolution & Volume Mount Synchronization in Docker
-------------------------------------------------------------------------
• Symptom / Problem:
  `dag_03_transform` failed when attempting to initialize DuckDB:
  `Catalog Error: Database path does not exist`.
• Root Cause:
  `docker-compose.yml` set `DUCKDB_PATH=/opt/airflow/data/warehouse/sdi.duckdb`,
  whereas Python modules defaulted to `data/duckdb/sdi_mart.duckdb`. Furthermore,
  the directory `/opt/airflow/data/warehouse` was not pre-created inside the container.
• Engineering Solution:
  Standardized environment configurations across `.env`, `docker-compose.yml`,
  and `src/transform/dwh.py`. Added automatic directory creation (`mkdir -p`)
  inside `src/transform/dwh.py` before initializing DuckDB connections, and verified
  persistent bind-mount mapping (`./data:/opt/airflow/data`).

3.4 Challenge 4: High-Volume Ingestion Optimization & Dirty Record Segregation
------------------------------------------------------------------------------
• Symptom / Problem:
  Staging 933,000 rows across 7 CSV files using standard SQL `INSERT` statements
  took upwards of 45 minutes, exceeding Airflow task execution timeouts.
• Root Cause:
  Per-row transactional logging (WAL) and index recalculations in PostgreSQL.
• Engineering Solution:
  Implemented a dual optimization:
  1. Configured staging tables as `UNLOGGED` during ingestion, bypassing WAL writes.
  2. Implemented Python in-memory streaming using `io.StringIO` and PostgreSQL's
     native `COPY stg.<table_name> FROM STDIN WITH (FORMAT CSV, HEADER TRUE)`.
  This slashed total staging ingestion duration from 45 minutes to under 28 seconds.
  Simultaneously, header validation and dirty string sanitization were embedded
  into `src/ingestion/loader.py`, isolating corrupt records to `data/rejected/`.

3.5 Challenge 5: Slowly Changing Dimension (SCD Type 2) Historical Tracking
---------------------------------------------------------------------------
• Symptom / Problem:
  Medicine prices, therapeutic classifications, and supply chain lead times
  evolve over time. A simple overwrite (SCD Type 1) would corrupt historical sales
  margin reporting for past transactions.
• Engineering Solution:
  Designed a pure SQL SCD Type 2 engine in `src/transform/dwh.py`.
  When a medicine price changes (simulated in Cycle 2 for 5 medicines):
  1. The existing record's `ValidToDate` is closed (`2025-09-30`) and `IsCurrent` set to `'N'`.
  2. A new record is inserted with a new surrogate key (`MedicineKey`), `ValidFromDate = '2025-10-01'`,
     `ValidToDate = '9999-12-31'`, and `IsCurrent = 'Y'`.
  3. Historical sales fact rows remain bound to the historical surrogate key,
     preserving exact historical margin calculations, while new sales bind to the current key.

5. SECTION D: DATA WAREHOUSE PROBLEM-SOLVING APPROACH & STAR SCHEMA

5.1 Dimensional Modeling Methodology & Grain Declaration

The Phase 1 SDI Data Mart was engineered strictly adhering to the dimensional
modeling blueprint established in the project design workbook (`excel`).

The design addresses two distinct business operational grains:
1. `fact_pharmacy_sale` (Transactional Fact):
   - Business Grain: One row per individual itemized medicine pack sold at a pharmacy.
   - Volume: ~500,000 baseline rows + 25,000 rows per refresh cycle.
   - Measures: `QuantitySoldPacks`, `GrossSalesAmountUSD`, `DiscountAmountUSD`,
     `NetSalesAmountUSD`, `CostOfGoodsSoldUSD`, `GrossMarginUSD`, `ReturnedQuantityPacks`.
2. `fact_hospital_demand` (Periodic Snapshot Fact):
   - Business Grain: One row per hospital, per medicine, per calendar month.
   - Volume: ~27,216 baseline rows + 1,500 rows per refresh cycle.
   - Measures: `RequestedQuantityPacks`, `ApprovedQuantityPacks`, `AllocatedQuantityPacks`,
     `FulfilledQuantityPacks`, `UnfulfilledQuantityPacks`, `FulfillmentPct`,
     `EmergencyOrderCount`, `StockoutIncidentCount`.

5.2 Dimension Engineering

The Star Schema incorporates 9 dimensions designed to maximize analytical flexibility:

1. `dim_medicine` (SCD Type 2):
   - Primary Surrogate Key: `MedicineKey` (BIGINT).
   - Natural Key: `MedicineID` (VARCHAR).
   - Attributes: `GenericName`, `BrandName`, `TherapeuticClass`, `DosageForm`,
     `Strength`, `PackSize`, `WholesalePriceUSD`, `RecommendedRetailPriceUSD`.
   - SCD-2 Attributes: `ValidFromDate`, `ValidToDate`, `IsCurrent` ('Y'/'N').
   - Problem Solved: Captures historical price changes accurately. When wholesale
     prices rise, historical sales maintain original margin calculations.

2. `dim_pharmacy`:
   - Surrogate Key: `PharmacyKey`.
   - Natural Key: `PharmacyID`, `PharmacyGLN`.
   - Attributes: `PharmacyName`, `PharmacyType` (Physical, Hospital, E-commerce),
     `City`, `State`, `ZipCode`.

3. `dim_hospital`:
   - Surrogate Key: `HospitalKey`.
   - Natural Key: `HospitalID`, `HospitalGLN`.
   - Attributes: `HospitalName`, `HospitalType`, `LicensedBeds`, `ICUBeds`,
     `TraumaLevel`, `AverageOccupancyRatePct`, `CatchmentPopulation`.

4. `dim_warehouse`:
   - Surrogate Key: `WarehouseKey`.
   - Natural Key: `WarehouseID`, `WarehouseGLN`.
   - Attributes: `WarehouseName`, `City`, `State`, `TotalCapacityPacks`.

5. `dim_date` (Role-Playing Dimension):
   - Surrogate Key: `DateKey` (Integer: YYYYMMDD).
   - Full Gregorian calendar spanning 2024 to 2026.
   - Attributes: `FullDate`, `DayOfWeek`, `DayName`, `CalendarMonth`, `MonthName`,
     `CalendarQuarter`, `CalendarYear`, `FiscalQuarter`, `IsWeekendFlag`.
   - Role-Playing Implementation: A single physical table joined multiple times:
     - In `fact_pharmacy_sale`: `SaleDateKey`, `DeliveryDateKey`, `ExpiryDateKey`.
     - In `fact_hospital_demand`: `RequestMonthDateKey`.

6. Junk Dimensions (`dim_sale_profile` & `dim_request_profile`):
   - Problem Solved: Low-cardinality discrete flags (ReturnFlag, PrescriptionRequired,
     DeliveryOTIF, PayerType, PaymentMethod, UrgencyLevel) threaten to clutter fact
     tables with dozens of foreign keys.
   - Solution: Extracted Cartesian product of operational flags into compact junk
     dimensions, reducing fact table width and accelerating scan speeds.

5.3 Conformed Dimensions & Future Constellation Readiness

The Phase 1 SDI schema is not an isolated silo; it is architected as the first lobe
of a full Enterprise Fact Constellation:
- `dim_medicine`, `dim_date`, and `dim_warehouse` are strictly conformed across
  future Phase 2 (Warehouse Inventory Mart: `fact_inventory_snapshot`) and
  Phase 3 (Manufacturing Mart: `fact_manufacturing_batch`).
- This shared dimensionality guarantees seamless drill-across capability, enabling
  queries that link pharmacy sales demand back to factory production batches
  and cold-chain IoT shipment excursions.

6. SECTION E: OVERSAMPLING & SYNTHETIC DATA GENERATION STRATEGY

6.1 Business Need & Strategy Rationale

In pharmaceutical enterprise architectures, historical static datasets fail to test
pipeline resilience, time-series continuity, and dimension versioning.
An oversampling and synthetic data generation module (`src/generator/generate.py`)
was engineered to:
1. Simulate continuous enterprise operational telemetry.
2. Provide predictable, realistic volume expansion (+10% volume increase).
3. Validate SCD Type 2 dimension splitting under active pipeline execution.
4. Stress-test data quality boundaries with simulated real-world anomalies.

6.2 Two-Cycle Refresh Simulation Architecture

The generator implements two distinct, parameterized operational cycles:

• Cycle 1 (Baseline Inflow: Q3 2026):
  - Temporal Window: July 1, 2026 – September 30, 2026.

6.4 Referential Integrity Preservation & Domain Constraint Rules

To prevent orphan foreign keys in the analytical warehouse:
1. Deterministic Seeding: Uses NumPy's `default_rng(_RNG_BASE + cycle)`, guaranteeing
   perfect reproducibility while preventing duplicate transaction IDs.
2. Parent-Child Constraint Enforcement: Every pharmacy sale references an existing
   `PharmacyID` and `MedicineID` present in master data.
3. Financial Balancing:
   `GrossSalesAmount = QuantitySoldPacks * UnitRetailPrice`
   `NetSalesAmount = GrossSalesAmount - DiscountAmount`
   `GrossMargin = NetSalesAmount - CostOfGoodsSold`
4. Domain Anomaly Injection:
   - 2% of sales simulate customer returns (`ReturnFlag = 'Y'`).
   - 15% of IoT telemetry records simulate cold-chain temperature excursions (>8°C),
     triggering operational warning flags in the BI dashboard.
